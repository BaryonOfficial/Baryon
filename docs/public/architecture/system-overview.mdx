This is an engineering map of the open Baryon engine. It helps you find the right
seam quickly when reading or changing the shared visualization code.

It is not a full code tour, and it is not the physics reference. For the governing
equations and the modal model, read the engine whitepaper alongside this page.

## The pipeline

The shared engine turns live audio into a volumetric cymatic field through one
mostly linear path:

```text
audio source
  -> Web Audio analyzers / live-input analysis
  -> CPU-side feature building
  -> AudioFeatureFrame
  -> visualization runtime
  -> render / output pipeline
  -> presentation
```

The defining property is that Baryon is **not** a generic audio-reactive renderer.
The audio side interprets musical and resonant structure first, and the render side
consumes that interpreted structure. Most "the visuals look wrong" questions are
really questions about which stage owns the behavior.

## Package ownership

The engine lives in two shared packages, consumed by the web app.

### `packages/visualizer`

Owns the engine and most domain semantics:

- audio analysis and feature extraction
- `AudioFeatureFrame` construction
- control schema, defaults, and runtime application
- visualization runtime factories
- render-quality / profile policy and output-pipeline composition
- the `raymarch` runtime implementation

Start here when a change affects shared visualization behavior.

Key files:

- `packages/visualizer/src/utils/audio/buildFeatureFrame.js`
- `packages/visualizer/src/utils/audio/audioFeatureEngine.js`
- `packages/visualizer/src/core/audio/`
- `packages/visualizer/src/controls/schema.js`
- `packages/visualizer/src/controls/runtime.js`
- `packages/visualizer/src/render/outputPipeline.js`
- `packages/visualizer/src/visualization/runtimeFactory.js`
- `packages/visualizer/src/core/raymarch/`

### `packages/app-shell`

Owns the shared React orchestration around the visualizer:

- control state lifecycle
- render-loop orchestration
- runtime diagnostics and performance-HUD state
- scene mounting and visualization host components

Start here when the engine itself is fine but state flow or render cadence looks wrong.

Key files:

- `packages/app-shell/src/components/hooks/baryonVisualizerRenderLoop.js`
- `packages/app-shell/src/components/hooks/useBaryonVisualizer.js`
- `packages/app-shell/src/components/hooks/baryonControlsState.js`
- `packages/app-shell/src/components/ThreeScene.jsx`

### `apps/web`

Owns the browser product shell: web app composition, browser acceptance and unit
tests, and web-only UX. Start here when the issue is web-shell-specific rather than
shared-engine behavior.

Host integrations that embed the engine wrap these shared packages rather than
forking their semantics. Their internals are out of scope for this public map.

## The main seam

The highest-value boundary in the engine is:

```text
audio analysis -> AudioFeatureFrame -> visualization runtime
```

That seam exists so that:

- audio interpretation stays renderer-agnostic
- render bugs can be debugged without rewriting analysis semantics
- a new runtime can consume the same authoritative feature structure

When a render symptom appears, the first job is to locate which stage owns it:

1. audio capture / live-input classification
2. feature extraction / `AudioFeatureFrame`
3. runtime / render consumption

See [Contracts and boundaries](/public/architecture/contracts) for what each of
these guarantees.

## Runtime lanes

### Audio ingestion and live-input semantics

`packages/visualizer/src/core/audio/` owns analyzer setup, device/input
classification, and live-input analysis policy — including the deliberate
distinction between line-feed / system-style input and acoustic microphone input.
Treat those input classes as intentionally distinct.

### Feature construction

`packages/visualizer/src/utils/audio/` builds two related but different artifacts:

- `AudioFeatureFrame` — the authoritative render-facing structure
- transport frames for the worker-backed audio feature engine

The transport frame is an internal optimization boundary, not the same contract as
`AudioFeatureFrame`.

### Render-loop orchestration

`packages/app-shell/src/components/hooks/baryonVisualizerRenderLoop.js` samples
analyzer state, prepares heavy-analysis inputs, builds or reuses feature frames,
drives adaptive raymarch behavior, and records runtime diagnostics. If frame pacing
or active-vs-idle behavior looks wrong, this file is usually on the critical path.

### Visualization runtime

`packages/visualizer/src/visualization/` owns visualization-method selection.
`raymarch` is the single supported method. Legacy persisted or synced values such as
`fullscreen-volume` and `cymatics-2d` collapse to `raymarch` at ingress; the field
is retained as a constant, with no user-facing visualizer selector.

### Render-profile resolution

`packages/visualizer/src/render/outputPipeline.js` is the public import path for
performance-profile and render-quality policy: profile normalization, render-scale /
TRAA / bloom resolution, and transparent-vs-opaque output composition. If a change
affects "Performance Profile" semantics, this file is part of the contract surface.

## State surfaces

### Control schema

`packages/visualizer/src/controls/schema.js` is the source of truth for control
keys, defaults, labels, runtime paths, method applicability, and whether a control
is live or debug-only.

### Persisted control state

Persistence lives in `packages/visualizer/src/controls/persistence.js` and
`packages/app-shell/src/components/hooks/baryonControlsState.js`. Only live controls
are serialized into presets and saved settings; debug-only controls are excluded.

### Runtime diagnostics

Diagnostics are assembled across
`packages/app-shell/src/components/hooks/baryonVisualizerRuntimeState.js`,
`baryonVisualizerRenderLoop.js`, and
`packages/app-shell/src/components/PerformanceHud.jsx`. Look here first when a report
is really about pacing, adaptive rendering, or method/profile state.

## Finding your way around

A quick index from symptom to starting point:

| If the issue is...                                      | Start in                                                                          |
| ------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Wrong live-input behavior                               | `packages/visualizer/src/core/audio/`                                             |
| Patterns look musically wrong                           | `packages/visualizer/src/utils/audio/buildFeatureFrame.js`                        |
| Render looks wrong but analysis seems plausible         | `packages/visualizer/src/visualization/` and `core/raymarch/`                     |
| Manual controls do not stick or load                   | `packages/visualizer/src/controls/` and `baryonControlsState.js`                  |
| Performance collapses only during active visuals        | `baryonVisualizerRenderLoop.js` and `packages/visualizer/src/core/raymarch/`      |

Before changing behavior near a seam, confirm whether you are changing **semantics**,
**transport**, or **presentation**, and whether the real contract is `AudioFeatureFrame`,
the control schema, or render-profile policy. When that is unclear, gather more context
before editing — the [contracts page](/public/architecture/contracts) describes which
boundaries are safe to move.
