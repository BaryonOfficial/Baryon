This page records the engine contracts that should be treated as stable unless a
change explicitly intends to move them.

The point is not "never refactor." It is to avoid accidental breakage at the
boundaries where Baryon has persisted settings, a worker-backed audio engine, and a
shared visualization core that more than one host can consume.

## The primary contract: `AudioFeatureFrame`

`AudioFeatureFrame` is the authoritative boundary between audio interpretation and
visualization:

- the audio side interprets signal structure
- the render / runtime side consumes that interpreted structure
- render code should not silently rebuild analysis semantics from raw audio state

**Safe changes**

- reducing allocation or redundant work while preserving frame meaning
- splitting feature construction into clearer internal stages
- adding fields that downstream consumers can safely ignore

**High-risk changes**

- changing the meaning of an existing field without a coordinated migration
- moving renderer-specific heuristics into the feature-frame contract
- papering over a render bug by mutating audio semantics ad hoc

When a bug appears near this seam, first decide whether it lives in capture/input
semantics, feature-frame construction, or runtime consumption. Do not skip that step.

### Modal visibility semantics

- `modalVisibilityEnergy` is an audio-owned signal derived from rectangular
  water-cavity modal excitation, persistence, coherence, and active-mode amplitudes.
- Low transient change must not suppress modal visibility; sustained ringing is valid
  cavity excitation.
- Renderers may use it to preserve local modal pressure-field visibility inside the
  spherical render hull, but not as a full-frame fallback tint, density wash, eigenmode
  switch, or independent mode promoter.
- The current physical model is:
  `audio drive -> rectangular water-cavity modes -> modal pressure field -> spherical render hull`.
- `Cavity Geometry` is a requested diagnostic surface today. Effective modal evaluation
  stays rectangular until a real alternate backend provides eigenfunctions, frequency
  families, field evaluation, and tests.
- Pressure and radiation carriers are normalized visualization quantities — not
  calibrated pascals, calibrated particle velocity, or proof of physical particle
  trapping.
- Appearance descriptors are deterministic audio-derived fields. They may affect color,
  iridescence, and style, but must not drive modal promotion, core structure, visibility,
  density, or performance salience.

### Spectral Light color

Spectral Light color is part of audio interpretation. When implemented, it is produced
before the render boundary and carried through the render-facing modal color slots — not
reconstructed from raw FFT bins inside the renderer.

The intended shape is:

- modal promotion decides which frequencies become render-facing structure
- Spectral Light colors only those promoted modes
- renderers spatially mix modal colors using the same modal fields that define the
  cymatic geometry
- a color value must not independently promote a mode
- the main render path must not add a global Spectral Light fallback tint

The detailed Spectral Light architecture lives in the engine whitepaper.

## Audio-engine transport frames

The worker-backed audio feature engine
(`packages/visualizer/src/utils/audio/audioFeatureEngine.js`) builds a transport frame
to enqueue analysis work, move compact analyzer state across the worker boundary, and
support internal scheduling and snapshot publication.

This transport frame is **not** the same thing as `AudioFeatureFrame`. Treat it as an
internal optimization contract, not the public semantic contract for visualization.

## Control surface

The authoritative control schema lives in
`packages/visualizer/src/controls/schema.js`. It defines stable control keys, defaults,
which controls apply to which visualization methods, runtime destinations, and which
controls are live versus debug-only.

If a value is persisted, transported, or consumed cross-host, its control key is part of
a compatibility surface. Changing a label is cheap; changing a key is not.

## Persistence

Persistence lives in `packages/visualizer/src/controls/persistence.js` and
`packages/app-shell/src/components/hooks/baryonControlsState.js`.

Current rules:

- only controls marked `live` are serialized
- debug-only controls are excluded from presets and auto-save
- deserialization starts from schema defaults
- unknown keys are dropped; missing keys fall back to defaults
- a limited set of legacy fields is normalized forward

So adding a new live control is usually safe if its default is correct, while removing or
renaming a persisted key requires explicit migration handling.

## Visualization method

Visualization methods are defined in `packages/visualizer/src/visualization/types.js`.
The only supported value is `raymarch`. Legacy persisted or synced values
(`fullscreen-volume`, `cymatics-2d`) collapse to `raymarch` at persistence and
stage-sync ingress. The field is retained as a constant for forward compatibility;
there is no user-facing visualizer selector.

These string values cross control applicability, runtime creation, diagnostics, and
tests. Do not rename them without coordinating all consumers.

## Performance profile

The canonical performance-profile contract is exported from the public import path
`packages/visualizer/src/render/outputPipeline.js`. (Internally the pure profile policy
may live separately from the WebGPU pipeline implementation; treat the `outputPipeline`
import path as the compatibility boundary.)

Canonical values:

- `auto` — adaptive performance behavior is active
- `custom` — adapts toward an explicit target frame rate (`Custom Target FPS`)
- `max-quality` — full quality at display-rate cadence; adaptive behavior is off

Compatibility alias still accepted:

- `none` — normalizes to `max-quality`

The user-facing wording is "Performance Profile," but some compatibility fields and
transport surfaces still use `qualityPreset` or `renderQualityPreset`. Treat that as a
naming boundary: the concept is the performance profile, and the older field names are
compatibility vocabulary that still matters. Do not rename them across the codebase
unless the task explicitly includes compatibility work.

## Line-feed versus acoustic-mic input

Input semantics are intentionally not uniform. Baryon distinguishes between:

- line-feed / system / loopback-style input
- acoustic microphone input

That distinction affects analysis-class choice, whether some raw time-domain data is
carried in transport frames, and expected behavior under live input. Changes that
"simplify" these into a single live-input mode are high risk unless the task explicitly
intends a semantic merge.

Acoustic-mic intent is a policy layer inside acoustic-mic semantics. `Ambient` and
`Vocal` should remain small gate-policy deltas over one shared acoustic input engine —
not separate analyzers, modal engines, or renderer branches. Acoustic source confidence
is input evidence only; it is not render authority.

## Rules for safe change

When you touch a boundary, ask:

1. Is this a semantic contract or an internal implementation detail?
2. Does this value cross persistence, transport, or host boundaries?
3. Are tests already asserting this string, key, or shape?
4. Do I need a compatibility alias instead of a rename?

Prefer canonical internal helpers, normalization layers, and dual-read compatibility
paths. Avoid broad string renames, schema-key churn, and payload-shape drift without an
explicit migration.
